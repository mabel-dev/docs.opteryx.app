# `x-flow` — call-sequence diagrams

The flow diagram on an API reference page — the numbered request/response ladder
between **Overview** and **Endpoints** — is rendered by
`update_docs_from_definitions.py` from structured data the service publishes.

## Who owns what

The **service** owns the content: which calls, in what order, what comes back.
**This repo** owns how it looks.

So a service publishes structured steps, never HTML and never Markdown. The
`api-flow` markup the renderer produces is meaningless without
`docs-site/app/globals.css`; putting it in a service repo would couple that repo
to this site's stylesheet and turn a restyle into a multi-repo migration.

## How a service publishes one

The flow lives in the service repo at **`docs/api-flow.json`**. Its
`scripts/export_api_docs.py` picks it up and emits it under a top-level
`x-flow` key, next to the existing `x-docs-public` convention:

```python
FLOW_KEY = "x-flow"
FLOW_FILE = Path("docs") / "api-flow.json"
...
openapi = _attach_flow(openapi, repo_root)
```

Nothing is hand-written into `definitions/*.json` — those are autogenerated
exports, and anything added here is destroyed by the next export, silently.

Services publishing a flow today: `upload.opteryx`, `jobs.opteryx`,
`authenticate.opteryx`.

## Shape

```jsonc
{
  "title": "Upload flow",              // section heading
  "intro": "Ingesting a dataset ...",  // one paragraph under the heading
  "actors": ["Client", "Upload API"],  // exactly two: caller, then service
  "steps": [ ... ],
  "notes": [ "**Sessions expire.** ..." ]   // markdown bullets under the diagram
}
```

Steps:

```jsonc
{"request": "POST /v1/upload/session"}              // numbered request rung
{"request": "POST /token", "note": "grant_type=refresh_token"}
                                                    // request, then " — " and the note
{"response": "201", "returns": "`session_id`, `url`"}
                                                    // numbered response rung
{"group": "Loop — for each file", "steps": [...], "note": "..."}
                                                    // labelled sub-sequence;
                                                    // "note" is optional, renders beneath
{"note": "..."}                                     // standalone note rung
```

Backticks inside `intro`, `returns`, and `note` become `<code>`. Write real `—`
and `·` characters; the renderer emits the HTML entities.

Numbering is assigned at render time, and only at the top level — steps inside a
`group` are alternatives or repeats, so numbering them would imply an order they
don't have. Never put numbers in the source.

## Two build checks

**Every `request` must name a route the same spec declares.** Rename or drop an
endpoint and the diagram breaks the build instead of quietly describing a call
that no longer exists:

```
api-opteryx-upload.json: x-flow references endpoints that are not in the spec:
['POST /v1/upload/{session_id}/finalise'] — the flow is out of date with the API.
```

Path-*parameter names* are normalised first, so a diagram may say
`{execution_id}` (the name the API hands back) where the route declares
`{identifier}`. Path shape and HTTP method still have to match exactly.

**A service known to publish a flow must keep publishing one.** `has_flow: True`
in `API_DOC_SPECS` means an export arriving without `x-flow` fails the build,
rather than silently dropping the diagram off the page — which is how these went
missing in the first place:

```
api-opteryx-upload.json: expected a `x-flow` block and found none — the service
publishes one from docs/api-flow.json, so this export is incomplete.
```

## Scope

One flow per service — the primary journey through that API. Every `request`
step must be one of that service's own endpoints; that's what the first check
enforces. A closing `note` that points onward is fine (the Authentication flow
ends by saying the token goes to every other API), but a diagram whose *steps*
run across several services has no owner — keep that in this repo as prose.
